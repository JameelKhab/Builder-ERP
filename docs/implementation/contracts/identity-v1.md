# Local identity and account provisioning contract v1

Original implementation for F239–F242/F266, M32 and the cross-cutting access requirement. Prior JAKH access evidence establishes separate roles/scopes, explicit reviewed changes and administrative boundaries; account-creation form evidence is recorded alongside this increment. Observations are not proof of source authentication internals or full parity.

1. Local real identities use individual username/password credentials. Demo actors remain explicit synthetic examples; the sample-login adapter is permanently disabled for a database once secure owner setup succeeds. No user-selected actor header or query parameter may establish identity.
2. First-owner setup is restricted to a loopback-only application with strict Host/Origin and same-origin write headers. It occurs once, creates a new owner identity, and explicitly reviews any initial company roles. User enters their own password; no password is invented, saved in source, sent externally or placed in a URL. An unassigned administrator can still reach company and user administration.
3. Passwords: 15–128 Unicode characters, normalization, no silent truncation, local weak/common-pattern checks, random salt and Node's scrypt (N=131072,r=8,p=1) with bounded concurrent work. Only salted hashes persist. Password managers/paste are allowed. No external password-check request or periodic forced reset. Comprehensive breached-password corpus, MFA/passkeys/SSO and independent security assessment remain release gates.
4. Sessions: random opaque 256-bit cookie, SHA-256 token digest at rest, HttpOnly/SameSite=Strict, 8-hour absolute and 30-minute idle expiry, current account and credential/access revision checks on every request. Real sessions survive ordinary restart, logout revokes the current session, password reset/change and access changes revoke authority. Sample sessions cannot access a secured database. Loopback HTTP is development-only; external hosting requires HTTPS and Secure cookies.
5. Sign-in is rate limited by normalized identity digest and global local-app attempt bucket, with persistent counters. Unknown/disabled/wrong-password cases return the same response. Password hashing and token consumption must revalidate state after asynchronous work. No error or audit record includes a password, session token, activation/recovery code or hash.
6. Access administrator creates a reviewed user identity and explicit role grants. Activation code is random, stored hashed, expires and can be used once; it is displayed once to the administrator for manual delivery. Nothing is sent through email/chat. Recipient chooses their own password. No shared default passwords. Existing source/example identities may be activated only through a separately reviewed binding.
7. Sensitive administration requires recent password reauthentication. Existing accounts/grants remain separate from administrative authority. No self-elevation; no disabling the last active configured administrator. Recovery/reset operations invalidate prior sessions and tokens. Offline one-use recovery codes are shown only to their owner; reset must not create access or alter roles.
8. Self-service account page shows current sign-in, active sessions, password change and recovery-code replacement with reauthentication. Account/access/security events are append-only and scoped; request/approval actor evidence uses the authenticated identity.
9. Preserve existing local data and examples. Tests use disposable credentials and databases; browser verification does not enter or change real user credentials. Bootstrap, activation, login, independent two-user business action, logout/restart/revocation, lockout, recovery, race/replay, mixed scopes and preview denial need end-to-end evidence before accepting this increment.
